# Деплой: как поднять сервис на реальном сервере

⚠️ Честно: Docker-файлы ниже написаны и логически вычитаны, но **не
прогонялись** в этой рабочей среде — здесь физически нет установленного
Docker. Перед реальным продакшен-запуском проверьте `docker compose up --build`
на своей машине/VPS и дайте знать, если что-то не собралось — это легко
починить. Весь остальной код (движок, backend, frontend) уже реально
запущен и протестирован, см. `docs/03-implementation-notes.md`.

## Архитектура деплоя

```
Интернет → (ваш домен, TLS) → nginx-контейнер (отдаёт React-сборку,
                                 проксирует /socket.io/ на backend)
                               → backend-контейнер (Node.js + Socket.IO,
                                 состояние столов в памяти + снимок на диск)
```

Один `docker-compose.yml` поднимает оба контейнера. Фронтенд и бэкенд
общаются по внутренней docker-сети, наружу торчит только фронтенд —
это и проще в настройке (не нужно думать про CORS с отдельным доменом
для API), и чуть безопаснее.

## Запуск локально через Docker

```bash
cp .env.example .env     # поправьте FRONTEND_ORIGIN, если нужно
docker compose up --build
```

Откройте http://localhost:8080.

## Запуск на VPS с реальным доменом

1. Поставьте Docker + Docker Compose на сервер.
2. Склонируйте репозиторий, создайте `.env`:
   ```
   FRONTEND_ORIGIN=https://poker.example.com
   PUBLIC_PORT=8080
   ```
3. `docker compose up --build -d`
4. Поставьте перед контейнером `frontend` (порт 8080) обратный прокси
   с автоматическим TLS — проще всего **Caddy** (один блок конфига,
   сертификаты Let's Encrypt сами) или **Traefik**/**nginx-proxy**,
   если уже ими пользуетесь. Пример `Caddyfile`:
   ```
   poker.example.com {
     reverse_proxy localhost:8080
   }
   ```
5. Готово — домен смотрит на Caddy, Caddy проксирует на контейнер
   фронтенда, фронтенд проксирует WebSocket на backend внутри
   docker-сети.

## Переменные окружения

| Переменная        | Где             | Назначение                                      |
|--------------------|-----------------|--------------------------------------------------|
| `FRONTEND_ORIGIN`  | backend         | Разрешённый Origin для CORS/Socket.IO            |
| `PORT`             | backend         | Порт backend внутри контейнера (по умолчанию 4000) |
| `DATA_DIR`         | backend         | Где лежит снимок состояния столов (по умолчанию `./data`) |
| `PUBLIC_PORT`      | docker-compose  | На каком порту хоста слушать nginx (фронтенд)    |
| `VITE_BACKEND_URL` | сборка frontend | Обычно не нужен — по умолчанию тот же origin, см. ниже |

### Почему не нужен отдельный URL для backend на фронте

`frontend/nginx.conf` проксирует `/socket.io/` на контейнер `backend`
внутри docker-сети. `frontend/src/lib/socket.ts` в продакшен-сборке по
умолчанию подключается к тому же origin, с которого загружена страница —
то есть к самому nginx, который прозрачно проксирует запрос дальше.
Отдельный `VITE_BACKEND_URL` нужен только если backend специально вынесен
на другой домен/поддомен.

## Персистентность

Backend раз в 30 секунд и при аккуратном остановке (`SIGINT`/`SIGTERM`,
именно так Docker останавливает контейнеры по умолчанию) сохраняет список
столов и стеки игроков в `DATA_DIR/tables.json`. В `docker-compose.yml`
это примонтировано как именованный volume `poker-data`, так что `docker
compose down && docker compose up` не обнуляет прогресс. Подробности и
сознательные ограничения (не сохраняется раздача в процессе) — см.
`docs/03-implementation-notes.md`.

## Что стоит сделать перед настоящим публичным запуском

- Прогнать `docker compose up --build` и сам сценарий игры руками минимум
  с двух разных браузеров/устройств.
- Ограничить `FRONTEND_ORIGIN` ровно вашим доменом (не `*`).
- Настроить логи/мониторинг (хотя бы `docker compose logs -f`).
- Решить вопрос с резервным копированием `poker-data` volume, если
  важно не терять стеки при пересборке сервера с нуля.
- Посмотреть на размер backend-образа — текущий Dockerfile копирует
  весь корневой `node_modules` монорепозитория в рантайм-образ ради
  простоты сборки; для продакшена стоит почистить лишнее (зависимости
  frontend там не нужны) — осознанный техдолг, а не баг.
