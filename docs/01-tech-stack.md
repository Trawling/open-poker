# Технологический стек: варианты и рекомендация

Главный критерий — та же философия, что у Lichess: **один человек/маленькая
команда должны суметь поддерживать это долго**, без тяжёлого DevOps и
микросервисного зоопарка. Простота важнее "модности" стека.

## Ключевое архитектурное решение: игровой движок отдельно от сети

Независимо от выбранного языка, сердце проекта — **чистый игровой движок**
(game engine) без сети и без UI:
- вход: текущее состояние стола + действие игрока ("колл", "рейз 200", "фолд")
- выход: новое состояние стола + список событий (кто сходил, вскрылся банк,
  определился победитель и т.п.)
- никаких побочных эффектов, никакого I/O — это чистая функция/модуль состояния
- это даёт: лёгкое unit-тестирование (прогнать тысячи раздач автоматически),
  возможность переиспользовать движок и для ботов, и для симуляций, и для
  "пазлов" (разбор рук) в будущем — аналог шахматных пазлов на Lichess

Поверх этого ядра уже накручивается realtime-слой (websocket, комнаты,
матчмейкинг, таймеры хода, reconnect) и фронтенд.

## Вариант A — Elixir + Phoenix (рекомендуется)

- **Почему подходит именно для покера:** Elixir/Erlang (BEAM VM) создан именно
  для задач "много независимых, изолированных, долгоживущих процессов с
  состоянием, которые общаются сообщениями" — ровно это такое стол в покере:
  каждый стол — отдельный лёгкий процесс со своим состоянием, падение одного
  стола не роняет остальные.
  - Явно описанные в комьюнити кейсы: "Building a Distributed Turn-Based Game
    System in Elixir" (fly.io), реальные карточные игры на Phoenix LiveView
    (проект Naiply — Brisca/Tute), статьи про Phoenix LiveView для мультиплеера.
  - **Phoenix LiveView** позволяет писать realtime-интерфейс почти без ручного
    JS — сервер рендерит обновления стола и пушит их в браузер через WebSocket
    автоматически. Это сильно сокращает объём фронтенд-кода для MVP.
  - Встроенные таймеры, супервизоры (автоматический перезапуск упавшего стола),
    "горячая" замена кода — удобно для сервиса 24/7 с минимальным даунтаймом.
- Минусы: меньше разработчиков знают Elixir, чем JS/Python/Go — может быть
  сложнее собрать контрибьюторов в open-source проект на старте.

## Вариант B — Node.js / TypeScript (самый простой вход для контрибьюторов)

- Самый большой пул потенциальных контрибьюторов для open-source проекта на
  GitHub — это важный фактор именно для "Lichess-like" амбиции (комьюнити
  должно уметь легко контрибьютить).
- Связка: Node.js (Fastify/NestJS) + WebSocket (`ws` или Socket.IO) для
  реалтайма + React/Svelte на фронте + Redis для состояния столов, если
  потребуется горизонтальное масштабирование на несколько инстансов.
- Движок пишется как чистый TS-модуль (см. принцип выше), тестируется Vitest/Jest.
- Минусы: состояние по умолчанию нужно явно шарить/синхронизировать между
  процессами/инстансами (в отличие от Elixir, где это встроено в модель акторов) —
  для одного процесса на старте это не проблема вообще.

## Вариант C — Go

- Отличная производительность, простое развертывание (один бинарник),
  неплохая экосистема для WebSocket (gorilla/websocket, nhooyr/websocket).
- Горутины + каналы неплохо ложатся на модель "один стол — одна горутина со
  своим состоянием", похоже по духу на Elixir, но без встроенной отказоустойчивости
  супервизоров из коробки (это пишется руками).
- Фронтенд всё равно отдельно (React/Svelte/Vue) + Go отдаёт только API/WS.

## Рекомендация для старта

Если важнее **скорость набора контрибьюторов и привычность стека** —
Node.js/TypeScript + React (или Svelte, он легче и тоже вписывается в
философию минимализма). Это самый низкий барьер для open-source комьюнити.

Если важнее **техническая элегантность и надёжность под реальный 24/7 realtime
сервис с минимальным DevOps** — Elixir/Phoenix (LiveView), это стек,
концептуально созданный именно под такую задачу.

Независимо от выбора:
- Движок игры — чистый, отдельный, тестируемый модуль (не зависит от выбора
  между вариантами A/B/C, легко переносится).
- Хранилище: на старте достаточно простого Postgres (пользователи, если будут
  аккаунты, журнал раздач, статистика) — без экзотики.
- Деплой: один сервер/один docker-compose на старте, как было у Lichess
  на старте — усложнять инфраструктуру только когда появится реальная нагрузка.

## Фронтенд / UI

- Минимализм как у Lichess: чистая типографика, нейтральная палитра, тёмная
  тема по умолчанию (меньше "вырви глаз" для долгих сессий игры), никакой
  казино-эстетики (мигающих фишек, аляпистых эффектов).
- Стол должен быть читаем на телефоне с первого MVP — мобильный браузер,
  скорее всего, будет основным способом "зайти и быстро сыграть".
