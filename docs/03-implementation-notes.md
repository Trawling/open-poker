# Что уже реализовано (рабочий MVP) и что ещё нет

## Структура кода

```
packages/engine/   — чистый движок No-Limit Hold'em (без сети, без UI)
  src/deck.ts            — колода + честная (provably fair) тасовка
  src/handEvaluator.ts   — оценка покерных комбинаций (5 и 7 карт)
  src/equity.ts          — Монте-Карло оценка силы руки (для бота)
  src/table.ts           — PokerTable: блайнды, улицы, ставки, сайд-поты, вскрытие
  test/                  — vitest: 15 тестов (комбинации, сайд-поты, честность, equity)

backend/            — realtime-сервер на Node.js + TypeScript + Socket.IO
  src/server.ts          — HTTP + WebSocket вход, снимок/восстановление состояния
  src/roomManager.ts     — создание столов, пул «быстрой игры», снимки
  src/tableRoom.ts       — обвязка движка: таймер хода, боты, безопасный выход
  src/bot.ts             — бот на основе equity + пот-оддсов
  src/persistence.ts     — сохранение столов на диск между перезапусками
  src/protocol.ts        — типы событий клиент↔сервер
  Dockerfile             — сборка образа backend

frontend/           — веб-клиент на React + Vite + TypeScript
  src/pages/Home.tsx     — главный экран («Быстрая игра» / «Создать стол»)
  src/pages/Table.tsx    — экран стола, сокет-подключение, таймер хода
  src/components/        — стол (сукно), место игрока, карта, панель действий
  src/styles.css         — минималистичная тёмная тема
  Dockerfile, nginx.conf — сборка образа frontend + прокси /socket.io/ на backend
  capacitor.config.ts, android/ — нативная Android-обёртка (для F-Droid),
    см. docs/05-android.md

docker-compose.yml  — поднимает backend + frontend вместе, см. docs/04-deploy.md

scripts/smoke-test.mjs         — сквозной тест: 2 клиента доигрывают раздачу
scripts/persistence-test.mjs   — реальный рестарт backend-процесса, проверка,
                                  что стек игрока пережил перезапуск
scripts/rebuy-test.mjs         — обнуление стека и докупка через реальный
                                  протокол (а не только юнит-тест движка)
scripts/chat-test.mjs          — сообщение в чате доходит мгновенно и
                                  попадает в историю (table:state) для
                                  переподключившихся
scripts/stakes-test.mjs        — уровни ставок применяются и разводят игроков
                                  по разным пулам быстрой игры
scripts/stats-test.mjs         — статистика обновляется после раздачи и
                                  доступна через REST; приватный турнир не
                                  добирается ботами сам по себе
scripts/tournament-test.mjs    — турнир целиком: рост блайндов, отказ в
                                  докупке, объявление победителя (может
                                  занимать до нескольких минут — это честная
                                  характеристика формата, не баг теста)
```

## Что работает прямо сейчас

- No-Limit Texas Hold'em, 6-max, один формат стола.
- Вход без регистрации — гость с автосгенерированным ником, id хранится
  в `localStorage` браузера (переживает обновление страницы).
- «Быстрая игра» — подбор в общий пул столов; если за 6 секунд не пришёл
  второй живой игрок, подсаживается бот, чтобы сразу можно было играть одному.
- «Создать стол для друзей» — генерируется приватный стол и ссылка вида
  `/table/<id>`, её можно скопировать кнопкой и отправить друзьям.
- Honest/provably fair раздача: до раздачи публикуется хэш server seed,
  после завершения раздачи сам seed раскрывается — в интерфейсе стола есть
  блок «Честность раздачи» с этими значениями (см. `packages/engine/src/deck.ts`).
- Корректная механика ставок: блайнды, колл/чек/бет/рейз, олл-ин,
  **сайд-поты** при разных по размеру стеках, возврат неуравненной ставки,
  определение победителя(ей) и разбиение банка при ничьей.
- Таймер хода (20 секунд по умолчанию): не успел — авто-чек или авто-фолд.
- Безопасный выход игрока: если раздача идёт, игрок уходит только после
  её завершения (не ломает чужую игру).
- Бот принимает решения на основе реальной оценки силы руки (Монте-Карло
  equity по `packages/engine/src/equity.ts`) и пот-оддсов, а не чисто случайно.
- **Турниры для друзей.** Кроме публичного «Быстрого турнира», можно
  создать приватный турнир по ссылке — в отличие от быстрого, он **не**
  добирается ботами автоматически (это стол для конкретной компании),
  но хост в любой момент может вручную добавить ботов существующей кнопкой.
- **Статистика игрока.** Привязана к коду личности (не к реальному
  аккаунту) — раздачи сыграны/выиграны, выигранные фишки, самый большой
  банк, турниры сыграны/выиграны. Хранится в памяти backend + сохраняется
  на диск тем же механизмом, что и стеки столов (`backend/src/stats.ts`,
  REST-эндпоинт `GET /api/stats/:guestId`, кнопка «Моя статистика» на
  главной). Не учитывает ботов.
- **Бот играет пуш/фолд с коротким стеком.** Ниже 12 больших блайндов
  (`backend/src/bot.ts`) бот перестаёт разыгрывать руку тонко и либо
  идёт в олл-ин, либо фолдит; ниже 5bb — почти никогда не фолдит (блайнды
  всё равно добьют за 1-2 круга, беречь фишки бессмысленно). Это не только
  реалистичнее, но и критично для скорости турнира: при первой, более
  мягкой версии порога бот иногда фолдил даже на коротком стеке и турнир
  с 3 игроками мог зависать на 10+ раздач без выбываний (поймано именно
  на CI, а не локально — см. историю коммитов). После ужесточения
  (плюс блайнды растут каждые 2 раздачи вместо 3) турниры обычно сходятся
  за несколько раздач, но дисперсия реальна и это нормально — иногда
  3-4 равно играющим ботам нужно много раздач, чтобы разобраться между
  собой, особенно пока блайнды ещё не критичны. Это не баг, а честная
  характеристика формата (в проверочном скрипте учтено запасом по времени
  до 8 минут — см. `scripts/tournament-test.mjs`). Отдельная находка по
  пути: пока разбирались с этим, можно было принять за баг "рост числа
  живых игроков" во время турнира — на деле это нормально: стек игрока,
  пошедшего ва-банк, становится 0 ещё **до** вскрытия (деньги уже в банке),
  и восстанавливается, если он выигрывает раздачу.
- **Три уровня ставок** (10/20, 50/100, 200/400 — `backend/src/stakes.ts`,
  зеркало на фронте `frontend/src/lib/stakes.ts`). Это просто разнообразие
  форматов игры, а не разная "цена входа" — фишки в любом случае виртуальные.
  Быстрая игра на разных ставках не сводит игроков за один стол.
- **Турнир Sit & Go (упрощённый, "турбо").** Отдельная кнопка на главной —
  без докупки, блайнды растут каждые 3 раздачи по расписанию
  (`backend/src/tournament.ts`), игра продолжается, пока не останется один
  игрок с фишками — он объявляется победителем прямо в интерфейсе. Честно:
  это не турнир с зафиксированным составом и призовой сеткой (такой стартует,
  когда заполнены все места) — можно зайти в любой момент, боты добирают
  стол через 6 секунд, если людей не хватает. См. оговорку в самом файле.
- **Докупка фишек.** Раньше игрок, проигравший весь стек, навсегда застревал
  за столом без фишек — это был прямой разрыв принципа «без гемора», найден
  и исправлен в этой итерации. Теперь интерфейс показывает кнопку «Докупить
  N фишек», как только стека не хватает даже на большой блайнд
  (`PokerTable.rebuy` в движке, `table:rebuy` в протоколе).
- Стеки и места переживают перезапуск backend-процесса: снимок состояния
  пишется на диск раз в 30 секунд и при graceful shutdown, восстанавливается
  при старте (`backend/src/persistence.ts`, проверено реальным рестартом
  процесса в `scripts/persistence-test.mjs`).
- **Чат за столом.** Отдельное событие `table:chat-send`/`table:chat` для
  мгновенной доставки (не ждёт следующего общего `table:state`), плюс
  история последних 50 сообщений, которая всё же едет в `table:state` —
  чтобы переподключившийся игрок увидел, что пропустил. Только живые
  игроки (боты не пишут), текст обрезается до 240 символов. Иконка с
  зелёной точкой непрочитанных в шапке стола, звук на новое сообщение.
- **Анимации.** Летящая фишка от игрока к банку при ставке и от банка к
  победителю на вскрытии (`PokerTable.tsx` — чистый CSS-transition по
  координатам, которые уже считаются для расположения мест за столом).
  Плюс более ранние: анимация раздачи карт, пульсация активного хода,
  подсветка победителя раздачи.
- Готов `docker-compose.yml` + Dockerfile'ы для деплоя на VPS одной командой
  (см. `docs/04-deploy.md`) — но сами образы не собирались в этой среде
  (здесь нет Docker), логика вычитана руками, рекомендуется проверить
  `docker compose up --build` перед продакшен-запуском.

## Чего нет и что стоит сделать дальше

1. **Персистентность — простая, не полноценная БД.** Сохраняются только
   места и стеки между раздачами (JSON-файл на диске), но не состояние
   текущей раздачи «на лету» — рестарт сервера прерывает текущую раздачу,
   следующая стартует заново с сохранёнными стеками. Для серьёзного роста
   нагрузки это стоит заменить на Redis/Postgres — см. `docs/01-tech-stack.md`.
2. **Один процесс.** Текущая архитектура не шардится между несколькими
   инстансами backend — это осознанно, ради простоты на старте (принцип
   Lichess «не усложнять раньше времени»), но ограничивает горизонтальное
   масштабирование. При росте нагрузки это первое, что нужно пересмотреть.
3. **Бот — улучшенный заполнитель, но не GTO-солвер.** Теперь он считает
   equity методом Монте-Карло и сравнивает с пот-оддсами (`backend/src/bot.ts`),
   что заметно осмысленнее случайных весов, но это всё ещё эвристика —
   не оптимальная стратегия и не замена живому сопернику.
4. **Упрощённое правило до-ставки (minimum raise reopening).** В редких
   граничных случаях (андер-рейз all-in на сумму меньше минимального рейза)
   действие у уже походивших игроков переоткрывается чуть шире, чем в
   строгих казино-правилах. На итог раздачи и честность это не влияет,
   отличие — только в редких тактических нюансах. Можно уточнить позже.
5. **Нет полноценных аккаунтов, статистики, истории раздач, рейтингов.**
   Вместо этого есть лёгкий, осознанно упрощённый механизм переноса личности:
   `localStorage` хранит случайный `guestId`, который можно скопировать на
   главной странице («Мой код для входа с другого устройства») и ввести в
   другом браузере — тогда вы продолжите с тем же стеком на тех же столах.
   Это **не** защищённый аккаунт (код = просто идентификатор, не пароль,
   им можно поделиться как ссылкой-приглашением) — полноценная система
   аккаунтов с почтой/паролем осознанно отложена, см. `docs/02-mvp-scope.md`.
6. **Нет автоматических e2e-тестов фронтенда** (только ручная проверка +
   `scripts/smoke-test.mjs`, который гоняет полную раздачу через реальный
   WebSocket-протокол без браузера). Добавление Playwright — хорошая
   следующая задача.
7. **Дизайн рабочий, но не финальный.** Сукно/карты/панель действий сделаны
   по принципам минимализма из `design/01-ux-principles.md`, но это не
   финальный визуальный язык проекта — можно и нужно дорабатывать.

## Реальные баги, найденные при отладке нестабильности турнирного теста

`scripts/tournament-test.mjs` долго падал в CI с разной картиной (иногда
"разошлось за 8 минут", иногда стол реально замирал навсегда). Вместо того
чтобы просто раздувать таймаут, искали и чинили настоящие причины — пять
разных багов, один за другим, методом живого воспроизведения (диагностические
скрипты-наблюдатели, подключавшиеся к уже зависшему столу прямо во время
прогона, плюс точечное временное логирование каждого шага timer-цепочки):

1. **Подбор "быстрого турнира" подсаживал новых игроков в уже идущий
   турнир.** `TOURNAMENT_MAX_SEATS` (6) больше, чем `TOURNAMENT_MIN_PLAYERS`
   (4) — это специально, чтобы в приватном турнире друзья могли подсесть
   перед стартом. Но `findOrCreateQuickTournament()` проверял только "есть
   ли физически пустое место", а не "начался ли уже турнир" — поэтому два
   места оставались вечно свободными, и новый игрок мог попасть прямо в
   разгар чужого турнира (раздача №18, блайнды 1000/2000) со свежим стеком.
   Это ломало инвариант "один закрытый состав до победителя" и давало
   бесконечный приток новых стеков, из-за чего число живых игроков не
   убывало. Исправлено: `TableRoom.hasTournamentStarted()`
   (`handNumber > 0`) теперь исключает такие столы из подбора.
2. **Блайнды не росли после последнего уровня таблицы (500/1000).**
   Оставшиеся в живых игроки забирают фишки выбывших, так что отношение
   стек/блайнд могло оставаться комфортным даже когда блайнды "вроде бы"
   росли — хедз-ап на фиксированных верхних блайндах мог стоять сколько
   угодно. Исправлено: `blindLevelForHand()` в `tournament.ts` после конца
   таблицы продолжает удваивать блайнды каждые `TOURNAMENT_HANDS_PER_LEVEL`
   уровней — рост теперь не ограничен (и сам шаг уменьшен с 2 раздач до 1,
   чтобы турбо-формат сходился быстрее).
3. **Защита от зависания при непредвиденном исключении.** `afterAction()` —
   центральная точка, вызываемая после любого действия человека/бота/
   автофолда по таймеру — нигде не была обёрнута в try/catch. Если бы
   что-то внутри (запись истории, проверка завершения турнира, эвристика
   бота `decideBotAction()`, которая раньше вызывалась вне try/catch в
   `runBotTurn()`) бросило исключение, следующий ход никогда не
   планировался бы — стол замер бы навсегда и молча. Это не оказалось
   фактической причиной найденных зависаний (ни разу не сработало на
   практике), но осталось реальной архитектурной дырой — закрыли её
   защитным обвязыванием каждого шага (`safeStep()`) с логированием, но
   гарантированным продолжением работы в любом случае.
4. **Главная находка — "фантомные" фишки из устаревшего `contributedTotal`.**
   `startHand()` обнулял `contributedTotal`/`contributedStreet`/и т.д.
   только для игроков-участников НОВОЙ раздачи, а не для всех занятых мест.
   У игрока, который отсиживает раздачу (`sittingOut=true`, уже выбыл или
   только что сел), оставалось старое значение `contributedTotal` от
   последнего раза, когда он играл. `goToShowdown()`'s возврат неуравненной
   ставки сканировал **все** занятые места (не только текущих участников)
   и мог по ошибке принять этот "хвост" за наибольшую ставку текущей
   раздачи — начисляя чужому, не участвующему в раздаче игроку чужие фишки
   "из ниоткуда". Из-за этого его стек становился ненулевым, но
   `sittingOut` оставался `true` — а `participatingSeats()` использует
   именно старое значение `sittingOut` как фильтр, так что игрок застревал
   исключённым из игры НАВСЕГДА, даже имея фишки. Когда таких "залипших"
   игроков набиралось достаточно, `canStartHand()` переставал находить двух
   участников, и турнир замирал без единой ошибки в логах. Исправлено в
   двух местах: `startHand()` теперь обнуляет per-hand поля ВСЕМ занятым
   местам без исключения, а `goToShowdown()`'s сканирование возврата ставки
   ограничено только НЕ отсиживающими текущую раздачу местами. Покрыто
   юнит-тестом в `packages/engine/test/table.test.ts`.
5. **Настоящий корень оставшихся зависаний — `tryStartHand()` не учитывал,
   что `startHand()` может мгновенно и полностью доиграть раздачу
   синхронно.** Если блайнды сразу загоняют игрока(ов) в ва-банк настолько,
   что реально действовать может максимум один оставшийся игрок,
   `PokerTable.startHand()` внутри себя вызывает
   `maybeFastForwardAllIns()`, которая синхронно прокручивает все улицы и
   доходит до `goToShowdown()` — раздача полностью завершается
   (`handInProgress = false`) ещё ДО возврата из `startHand()`. Но
   `TableRoom.tryStartHand()` слепо вызывал `this.broadcast();
   this.scheduleNextActor();` сразу после `startHand()`, предполагая, что
   кто-то обязательно должен ходить. `scheduleNextActor()` в этом случае
   видит `actingSeatIndex === null` и `handInProgress === false` — условие
   для аварийного восстановления (`forceEndHand`) не срабатывает
   (раздача и так уже корректно завершена!), и функция просто молча
   возвращается. В итоге: клиенты видят финальное состояние раздачи
   (showdown, победители), но `scheduleAutoStart()` для следующей раздачи
   никогда не вызывается — стол висит вечно. Это и есть причина
   большинства "зависаний без единой ошибки в логе", которые тест ловил
   нестабильно (воспроизводится, только когда короткий стек реально
   загоняется в ва-банк прямо на блайндах — довольно специфичное, но не
   редкое при турбо-блайндах стечение обстоятельств). Исправлено:
   `tryStartHand()` теперь вызывает единую точку `afterAction()` вместо
   прямого `scheduleNextActor()` — она уже корректно умеет обработать оба
   исхода `startHand()`. Покрыто юнит-тестом, явно моделирующим мгновенный
   ва-банк на блайндах.

Находки 4 и 5 — единственные, что реально и стабильно вызывали зависания:
воспроизводили вживую (диагностический клиент-наблюдатель, подключавшийся
к конкретному зависшему `tableId` прямо во время прогона, показывал точное
состояние стола и подтверждал отсутствие прогресса), затем чинили и
перепроверяли десятками последовательных прогонов `tournament-test.mjs`
(финальная проверка: 10 из 10 прогонов подряд успешны, без единого
зависания, см. историю коммитов).
